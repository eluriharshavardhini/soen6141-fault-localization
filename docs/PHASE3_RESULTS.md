## The techniques (same information, same caps, different use of the budget)

All techniques see only what the baseline is allowed to see: the failing tests, their
output, the buggy source tree, and the test code the benchmark adds. They never see the
oracle, the fix message or the fixed code.

* **Candidate retrieval (shared, no model).** Every function in the buggy source tree is
  indexed. Functions on the stack trace come first, deepest frame first. The rest are
  ranked by BM25 text similarity to the failure output and the test code. An oracle function
  is among the top 30 candidates for 44/63 bugs, and among the top 4 for 29/63.
* **T1 retrieved context (1 call).** The baseline question, plus the test code, the list of
  30 candidates with their signatures, and the source of the top 4.
* **T2 inspect-then-rank (2 calls).** First the model sees the candidate list and picks up to 5
  functions to read. Then it sees their source and gives its ranking. The model, not the
  retriever, decides which code to look at.
* **T3 self-consistency vote (3 calls).** The T1 prompt is sampled 3 times at temperature 0.7,
  and the three ranked lists are merged by Borda count (5 points for rank 1, 4 for rank 2, ...).
* **Ablation: baseline prompt + vote (3 calls).** The same voting, but over the baseline
  prompt, with no code shown.

## What we learn

1. **Showing the right code is what helps.** All three techniques improve function Top-1 by
   16 to 24 points for both models. T2 and T3 stay significant after Holm correction, and
   all MRR confidence intervals exclude zero.
2. **More calls alone do not help.** Voting over the baseline prompt uses the same 3 calls
   as T3 but adds only 2–3 points, which is not significant. The gain comes from the
   retrieved context. Voting adds a smaller, non-significant extra on top of it.
3. **The models add real value over retrieval.** The retriever's own first guess is right
   for only 15.9% of bugs. With the same candidates, the models reach 40–54%.
4. **The ceiling is retrieval.** 18 of the 29–38 remaining misses per technique are bugs
   whose fixed function is not among the 30 candidates. Most remaining errors are
   retrieval misses, not ranking misses, so better retrieval (for example coverage-based
   spectrum FL) is the clearest next step.
5. **Hardest project: black.** At most 2/10 bugs are solved there. For 7 of its 10 bugs,
   the failing test compares formatted output with an expected file, so the stack trace stops
   in the test helpers and never names any formatter function.
6. **A cost of reasoning models.** Qwen produced no answer on 16/63 bugs in T1 and 15/63
   in T2, because it spent the 1,500-token limit on hidden reasoning once code was shown.
   Voting cut that to 7/63, which explains part of T3's gain for Qwen. gpt-oss never ran out.
7. **Contamination control.** On the 15 bugs fixed after Qwen3.8's release, which it cannot
   have seen, the ordering holds: baseline 26.7%, T1 46.7%, T2 40.0%, T3 53.3%. gpt-oss's
   cut-off (June 2024) predates all 63 bugs.

## Threats to validity

* **Small n.** There are 63 bugs (15 post-release for Qwen), so per-repository numbers and
  differences between techniques have wide uncertainty. We report paired tests and CIs, not
  only point estimates.
* **Budget equality is a cap, not equal spending.** Every technique has the same caps
  (≤3 calls, same input and output limits), but they use different amounts within them:
  tokens per bug range from about 3k (T1) to 12k (T3). The ablation shows that extra calls
  without context do not explain the gains.
* **Any-match oracle.** 15 bugs have several oracle functions, which makes those easier.
  The single-function subset is reported in Phase 2.
* **Deviations from the proposal.** (a) The non-LLM reference is stack trace + BM25 instead
  of spectrum-based Ochiai. Ochiai needs the full test suite run with coverage for every
  bug, which did not fit the deadline. (b) Technique B is "inspect-then-rank" (the model
  chooses code to read) instead of refinement with test-execution feedback, which would need
  a Docker run inside the loop for every bug. (c) T1 and T2 are single runs at temperature
  0. T3 and the ablation sample at temperature 0.7 with fixed seeds.
* **Hosting.** gpt-oss runs on Groq. Qwen runs on one OpenRouter host (Wafer). The provider
  may change quantization over time. Every response is cached, so the published numbers
  stay exactly reproducible.
